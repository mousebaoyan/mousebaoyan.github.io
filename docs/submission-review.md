# 投稿审核与自动发布

## 管理员日常操作

1. 打开投稿 Issue，阅读文章或资源信息。
2. 如需修改，点击 **Issue 正文右上角的 `…` → Edit**，修改字段内容并保存。请保留 `### 标题`、`### 正文内容`、`### 标签（选填）` 等表单字段标题及其顺序。文章正文可以自由使用多级 Markdown 标题、列表、图片和代码块。
3. 在右侧 **Labels** 添加 **`审核通过`**。
4. 等待 Actions 完成。系统会校验字段、构建网站、提交内容并部署 GitHub Pages；成功后在 Issue 中给出页面链接并关闭 Issue。失败时保留 Issue，并附上发布日志。

经验贴和资源推荐都支持。旧投稿不需要重新填写，也不依赖「投稿」「经验贴」等分类标签；系统根据表单字段识别类型。

审核者需要仓库 **Write / Maintain / Admin** 权限。只有 Triage 权限的成员即使能添加标签，也不能触发内容发布。

正文支持 Markdown，不支持原始 HTML。HTML 示例请写在代码块里；图片请上传到 GitHub Issue 或使用完整的 HTTPS / HTTP 地址。

## 发布后修改

1. 重新打开原 Issue。
2. 编辑 Issue 正文，保存并检查内容。
3. 移除原来的 `审核通过` 标签，再添加一次。

系统会更新同一个文件和页面，地址不会改变。编辑 Issue 本身不会自动更新网站；作者修改已发表投稿后，也需要管理员重新审核。

每次发布采用**添加标签时的正文版本**。如果构建期间正文又被修改，或审核标签被移除，提交前会停止并要求重新审核。如果内容已提交后 Issue 又发生修改，部署仍使用已经审核的内容，Issue 会保持打开，提示再次审核。

文章按 Issue 编号保存为：

- 经验贴：`src/content/experiences/submission-<编号>.md`
- 资源：`src/content/resources/submission-<编号>.md`

生成文件的 `sourceIssue` 记录原投稿链接；经验贴日期使用投稿创建时间（北京时间），再次发布不会改变日期。自动生成内容默认公开、非首页精选。

请把 Issue 作为自动发布内容的编辑来源。直接修改生成文件后，再次审核会以 Issue 内容重新生成，包括 `featured` 等默认字段。如需手动管理首页精选等属性，可在最后一次审核后修改文件，并在以后再次审核时留意这些字段。

移除标签或关闭 Issue 不会下架已发布内容。下架请通过普通代码修改删除内容文件；再次审核会重新公开。

## 首次配置

1. 将此功能的代码推送到仓库默认分支（当前为 `main`）。GitHub 的 `issues` 事件只执行默认分支上的工作流。
2. 在仓库 **Issues → Labels** 创建 `审核通过` 标签。建议同时创建表单中的 `投稿`、`经验贴`、`推荐资源` 分类标签。标签名必须完全一致。
3. 仓库 **Settings → Pages → Source** 使用 **GitHub Actions**，并允许 GitHub Actions 运行。

工作流会按任务声明 `contents: write`、`issues: write`、`pages: write` 等所需权限。使用 GitHub 自动提供的 `GITHUB_TOKEN`，**不需要个人访问令牌或新增 Secret**，也不需要开启「Allow GitHub Actions to create and approve pull requests」。

如果仓库或组织策略禁止工作流写入，或默认分支保护要求所有更改必须经过 PR，本流程会报告提交失败；需由仓库管理员调整对应策略后才能使用直接发布。流程不会绕过分支保护。

## 失败与重试

- **字段错误**：按 Issue 中的错误提示修正内容，再移除并重新添加审核标签。
- **构建失败**：查看评论中的 Actions 日志，修复后重新审核；构建失败的投稿不会写入仓库。
- **提交失败**：检查权限、分支保护，或构建期间是否有人改动同一篇文章。处理后重新审核。
- **内容已提交、部署失败**：修复部署问题后，在 Actions 中重新运行失败任务即可。相同内容不会重复提交。
- **审核期间 Issue 被编辑**：检查最新内容后重新添加标签。不要通过重跑旧任务来发布新的内容。
- **状态评论失败**：网站可能已经发布；先查看 Actions 的部署结果，再重跑失败任务即可。

同一条 Issue 的工作流串行执行。不同投稿可以并发，提交时只改动目标文件，并针对分支并发写入冲突有限重试；不会覆盖构建期间对同一文件的新修改。

## 实现与维护

- `.github/ISSUE_TEMPLATE/*-submission.yml`：投稿字段定义，同时作为解析和表单校验的来源。调整字段标题时只需修改模板；已有投稿若仍使用旧标题，应先编辑到新格式。修改字段 ID 或增加字段时，还应更新转换映射和测试。
- `scripts/submissions/convert.mjs`：纯内容转换。使用 Markdown 语法树识别表单边界，完整保留正文标题和代码块；使用 YAML 序列化生成 frontmatter。
- `scripts/submissions/publish.mjs`：权限检查、审核版本核对、提交与状态反馈。
- `.github/workflows/publish-submission.yml`：审核、构建验证、提交、部署与结果反馈。
- `.github/workflows/deploy.yml`：供普通推送和审核发布共用的部署流程。机器人使用 `GITHUB_TOKEN` 提交后不会触发 `push` 工作流，因此审核工作流会显式调用部署。排队部署开始时拉取最新默认分支，避免较旧快照覆盖较新网站。

本地验证：

```sh
npm ci
npm test
npm run build
```

测试覆盖两类投稿、复杂 Markdown、特殊字符、字段校验、编辑后再审核、权限拒绝、审核撤回、并发写入、重复执行以及部署成功和失败的状态反馈。
